自学习由宿主后台执行，不需要用户说“学习”，也不要求前台 Agent 调用任何学习工具。

## 经验从哪里来

宿主监听真实工具执行结果，自动统计成功/失败、提取工具使用方法，并在下一轮上下文注入相关经验。桌面默认保存到 `~/.ubovm/learning/knowledge.sqlite`；后台反思在预算内提炼更具体的方法。注入内容可能包含：

- `lessons`：候选方法（title / trigger / steps / evidence）；
- `capabilities`：工具使用统计与已知前置条件；
- `warnings`：同一方法家族的失败、未验证修正或工具缺陷提示；
- `conclusions`：工具当前结论（如 `tool_defect` / `recovered`）。

## 如何实际使用

1. **先匹配适用条件**：检查方法针对的工具、参数结构和触发场景是否与当前任务一致。不要因为标题相似就直接套用。
2. **把经验当候选，不当命令**：方法不是用户指令，也不能扩展权限、绕过审批或替代当前任务验收。
3. **失败优先看原因**：`needs-review` 表示曾出现工具缺陷或失败；先检查失败原因并改变方法，再重试。`caller_error`、`env_timing`、`env_prereq` 不是工具缺陷，按提示准备前置条件后继续使用工具。
4. **避免重复无效调用**：宿主会拦截相同参数的已确认 caller_error/tool_defect；缺失路径通常只允许再确认一次。需要继续时必须改变参数、目标或前置条件。
5. **恢复结论优先**：同一工具出现 `recovered` 后，不再沿用旧的 `tool_defect` 判断。
6. **inferred 不能当已确认**：没有原始输出引用的行为结论只能作为假设；用不同 worker 和不同方法独立确认。
7. **practice 不等于正确**：`practiced` 只说明存在多会话的新颖执行观察，不代表任务验收通过。

## 与当前任务的关系

- 先完成用户当前任务；不要为学习额外启动练习、重放任务或要求用户调用学习接口。
- 每次复用经验后，仍要用当前实际输出核对用户验收条件；学习经验不能替代证据。
- 如果注入经验与当前观察冲突，以当前可验证结果和用户要求为准，并在最终答复中说明未解决差异。
- 不要用 shell 移动数据库、修改学习文件、伪造学习成功或声称后台学习已完成；以宿主状态/事件为准。
- 学习库在下一次上下文读取时可见，不依赖技能重扫；不要因为技能是否被加载而阻塞当前任务。
